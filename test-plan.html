Test Plan

Test plan I wrote for an online school platform (training environment), covering the sign-up and login features.

Introduction

The platform is an online school offering courses for in-demand careers. Through the website or app, students access courses with qualified instructors, delivered through video lessons and assignments. The site must be accessible from any computer or mobile device connected to the internet. Core features: sign-up, login, and content access.

Architecture

The implementation framework is cloud-based.

Features

FeatureExpected behaviorVerificationsAcceptance criteria
Sign-up After entering name, e-mail, phone number, and password and clicking "Sign up", the user is redirected to the success page and receives an account-activation e-mail.
  • Minimum 8-character password with letters, numbers, and special characters
  • Redirect to the success page
  • Failure message for duplicate user
  • Failure message when the password doesn't meet minimum requirements
  • Failure message for missing/incomplete required fields
  • New e-mail address
  • Valid password
  • Valid phone number
Login Entering a valid e-mail and password logs the user into the platform. A user already logged in on another device must be able to log in again.
  • Successful login
  • Invalid user
  • Invalid password
  • Required field not filled
  • Invalid phone number
  • System accessibility
  • Correct screen redirect

Test Strategy

Scope

This plan covers all features described in the table above. Video-lesson playback is out of scope.

Testing will run at all levels:

  • Non-functional testing — usability and performance testing to detect improvement opportunities.
  • Automated testing — end-to-end tests for the login and sign-up features.
  • Manual testing — all features tested manually by the QA team, following the test scenario documentation and this Test Plan.
  • Beta release — a beta version released to 30 pre-registered users before the public release.

Environment & Tools

Tests run in the staging environment, configured identically to production, with test data previously generated by the QA team.

Bug Severity Classification

1BlockerBlocks testing of a function or feature; crashes the application; a broken button prevents using the feature entirely; blocks the release
2MajorFeature does not work as expected; unusual input causes irreversible effects
3ModerateFeature misses some acceptance criteria but works overall; success/error message not displayed
4MinorAlmost no functional impact but hurts the experience; typos; small UI glitches

Definition of Done

A feature is considered done when it passes all verifications and tests described in this Test Plan, has no open bugs above Minor severity, and passes a business validation owned by the product team.

Test Plan — Final Project: "Wheat Lovers" website

For the final project of my QA studies, I started from a user story and built the test plan for a company website:

"As a business owner in agriculture, I want to validate the functionality of my new website. I need something simple and intuitive."

The plan followed the same structure as above (introduction, features with acceptance criteria, strategy, severities, Definition of Done), focused on usability: working menu links, readable text, and a phone-number interest form accepting only valid numbers.

The test cases and bugs found in this project are in Test Cases and Bug Reports.
